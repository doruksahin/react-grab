Where the production token is
In the deployer's macOS Keychain, and nowhere else outside Cloudflare. Print it only to paste it somewhere:
security find-generic-password -s react-grab-sync-prod -a SYNC_API_TOKEN -w
To deploy a change
pnpm --filter @react-grab/sync-server db:migrate:prod
pnpm --filter @react-grab/sync-server publish:worker
Migrations first, so the new code never meets an old schema. Secrets survive a redeploy.
It is on a personal account
One person's login is the only way in, and nothing in CI can deploy it. Move it to a company account before anyone depends on it: change account_id, create D1 and R2 there, run the migrations and set the three secrets again.

Daily

Running the stack

First run, once
pnpm install && pnpm build
pnpm --filter @react-grab/sync-server db:migrate:local
The build writes the type definitions that watch mode then preserves. Without it the host app cannot resolve react-grab types.
Terminal 1 — library
pnpm dev
JS only, 15–20s a rebuild. Use pnpm dev:full when changing public types.
Only when changing the server
pnpm sync:dev
Everything else uses the deployed Worker, locally too. Run this on :8787 only to test server code, and point serverUrl at it meanwhile.
Terminal 2 — host app
pnpm dev
In AdCreative-Frontend-V2, whose node_modules/react-grab symlinks here.

When it breaks

Known traps

Two builds racing
Never run pnpm build while pnpm dev is watching elsewhere. Two tsup processes on one dist/ corrupt the output and wedge the watcher. Stop the watcher first.
Failed to resolve entry for "react-grab"
The host app started mid-rebuild and cached the failure.
rm -rf node_modules/.vite
Run it in the host app, then restart its Vite.
Jira returns 401
A wrong value, not a missing one — since ADR-0018 an empty value fails loudly on the first request instead. Check the account and token in .dev.vars, then restart pnpm sync:dev.
Every sync request returns 401
The overlay's token does not match the server's. Compare VITE_REACT_GRAB_SYNC_TOKEN in the host app with SYNC_API_TOKEN in .dev.vars (or production's), then restart both.
Tickets land in the wrong place
Site and project are set in different repositories. Read the second diagram again — that is almost always the cause.
