1 · Context

Three runtimes, two trust boundaries

The overlay runs inside someone else's app, in a browser. Everything it persists goes over the network to one Cloudflare Worker, which is the only thing that holds Jira credentials.

2 · Boot

What happens when the host app starts

Architect's read. Polling cost grows as groups × open tabs. With ten people each watching twenty ticketed groups, that is 200 Jira reads every 30 seconds, all on one service account's rate limit. Fine at today's size; the first thing to break at scale.
3 · Capture

Commenting on an element

Architect's read: lost updates, fixed. Until ADR-0019 a save sent the whole list and the server deleted every comment before inserting the tab's copy, so whoever saved second erased the first person's new comment. Each write now targets one comment. What remains is narrower: two people editing the same comment at once, where the last write wins.
4 · Ticket

Creating a Jira ticket

Architect's read. Step 11 files into whatever project the request names. The server validates that it is a string and nothing else, and the Jira credential can write to every project its account can reach. Since ADR-0020 only callers holding the sync token can send this request, so this is a trust-the-team issue, not an open door.
5 · Decided and shipped · ADR-0020

The gate in front of every data route

Two checks run before the middleware that touches storage or Jira, so no data route is reachable without them. /health, /doc and /ui stay public.

Why a shared bearer token. Cloudflare Access was the other candidate, but it answers a CORS preflight with 403 because preflights carry no credentials, so a cross-origin overlay cannot use it without extra configuration. A single token is the least moving parts for a handful of trusted callers. Its limit: anyone with the token reaches every workspace. Per-workspace keys are the next step if outside teams ever call the Worker. Full reasoning in decree/adr/0020-bearer-token-and-origin-allowlist-for-the-sync-server.md.
Decided and shipped · ADR-0019

Lost updates, and why they could duplicate a Jira ticket

Clients load comments and groups once at start-up. They used to save by sending the whole list, which the server wrote over everything it had. The sharpest consequence was not a lost comment but a lost ticket link, which disarmed the guard that prevents duplicate tickets.

Why this and not If-Match on the whole list. A version check on the list is the textbook lost-update guard, but every rejected save would need the client to refetch, merge and retry — the merge is the custom logic we would then own. Per-item writes remove the conflict for different items outright; If-Match stays in reserve for the rare case of two people editing the same item. Full reasoning in decree/adr/0019-per-item-writes-for-comments-and-groups.md.
